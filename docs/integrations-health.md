# Integrations and operational health

`GET /admin/api/v1/integrations` requires platform `integrations` permission. `POST /admin/api/v1/integrations/:key/update` accepts `{version, enabled, reason}`. The required reason is trimmed (5–500 characters). Each update locks the registry record, checks its version, increments it, and records append-only configuration history, immutable platform audit and an outbox event in one transaction. Stale writes return 409. Secrets and arbitrary provider URLs are not accepted.

The registry stores **requested availability**, separately from connectivity. All ten seeded provider definitions start disabled. Enabling a definition shows `unconfigured`: no external provider adapter, credentials, webhook handler or company binding has been provisioned. Company count is zero; sync times, error counts and webhook URLs are unavailable. Configuration history is real and is labelled accordingly. This module does not yet process vendor payments, send messages, import leads or upload objects. Configure and implement the individual connector before exposing it to company users.

`GET /admin/api/v1/system-health` requires platform `health` permission. PostgreSQL probes verify both restricted database roles and schema access; Redis is pinged. Checks fail closed, return generic errors and have a six-second response deadline. The dashboard polls every 30 seconds and marks previous results stale if refresh fails. Session validation still requires PostgreSQL, so use public `/health/ready` or external monitoring when login/database access is unavailable.

Telemetry measures HTTP requests completed through the application middleware (including public readiness and monitoring traffic). Hourly UTC buckets retain at most 24 hours in this API process; HTTP 5xx are server errors, with 4xx counted separately. Latency percentiles cover the latest 10,000 completed requests. Process uptime, resident memory and the API's two database pools (combined maximum 20) are actual measurements, not host-wide metrics. Metrics reset when the process restarts and are not shared across replicas. No historical availability SLA, CPU, storage capacity or active-job claims are made. Storage/jobs remain explicitly uninstrumented. Alerts reflect current failed dependency probes, not simulated historical incidents.

After applying migration 007 and provisioning the Super Admin, run `npm run db:seed:integrations` with the owner `MIGRATION_DATABASE_URL`. It inserts only missing catalog records, audits each creation, and preserves existing settings on reruns. Health needs no fabricated seed data; live traffic starts measurements automatically. On staging, run the maintenance container with `node scripts/seed-integrations.mjs` after deploying. No new runtime environment variables or GitHub secrets are required.
