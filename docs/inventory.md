# Company projects and units

Migration 015 introduces real projects, phases, buildings and units with forced company RLS, composite parent foreign keys and existing owner permission upgrades. New owners receive projects.read/manage and units.read/manage. All APIs enforce current company subscription access; tenant context comes exclusively from the session. Codes are normalized to uppercase and unique within a company (phase/building codes within their parent).

Projects expose paginated search and archived filters at GET /api/v1/projects. GET /:id returns saved phases/buildings plus counts calculated from active units, including under-contract counts and the minimum available-unit price. No generated stacking cells or invented totals. Units are paginated separately by building, project, listing, type, status and search at GET /api/v1/units; GET /:id supports direct links. Project details and unit results use consistent read snapshots.

POST /projects creates; /:id/update edits with version. /:id/phases creates a phase; /:id/phases/:phase/update edits it. /projects/phases/:phase/buildings and /:building/update create/edit buildings. Phase delivery years and building heights are validated; a height cannot be reduced below existing unit floors. Parent creation/editing requires an active project and preserves history.

POST /units and /:id/update accept exact EGP priceMinor strings, area (up to two decimal places), type, bedrooms, view, location, listing and optional building/floor. Rental prices are monthly. Primary units require a company building; building-linked units need a valid floor within its height. Standalone resale/rental units are supported. New units start available; reservation and contract statuses cannot be forged through inventory forms. Only active available units can be edited. GET unit responses preserve exact prices as strings; the dashboard uses BigInt conversions.

POST /projects/:id/archive and /units/:id/archive accept action archive/restore and current version. Project archival requires its units to be archived first. Restoring a building-linked unit requires an active parent project. No hard deletion. Mutations use the shared request UUID replay ledger and company write lock; state/audit/outbox/replay commit atomically and stale versions conflict.

Creation and restoration enforce the current subscription projects/listings limit (null means unlimited; zero forbids creation). An unexpired platform listing override replaces the base listing limit. Forced-RLS unit counts and the narrow, company-filtered inventory policy view are used inside the company write transaction. The tenant role can read that policy view but cannot read platform subscription/plan tables. Platform usage reads an aggregate active-listing view; storage measurement remains unavailable until a real storage module supplies it.

Both screens preserve the bilingual design and expose actual create/edit/archive/restore forms. Project/phase/building management is separate from units. The stacking plan loads and paginates saved building units. Incomplete reservation/contract actions are not simulated by changing a client-side status.

Run npm run db:seed:inventory with isolated migration credentials, or node scripts/seed-inventory.mjs --company-slug=your-slug in the maintenance container. Default targets are only the three labeled sample companies with current subscriptions. It adds one sample project/phase/building plus three sample available primary/resale/rental units per eligible company, respecting limits. Explicit-company seeding is opt-in; reruns preserve existing edits and archived samples. No fake sold units, financial transactions or identities are created. Seeding is explicit; migrations run automatically during staging deployment. No new secrets are required.
