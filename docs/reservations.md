# Company reservations

Migration 016 adds company reservations and upgrades existing/new company owners with reservations.read/manage. Company APIs require the current subscription. Creation additionally requires units.read and leads.read. All records use forced RLS and same-company unit/lead/user foreign keys. A partial unique index permits only one active hold/reservation per company unit.

GET /api/v1/reservations supports pagination, search, unit/lead filters and status. GET /:id returns actual unit/lead/assignee references, exact deposit strings, expiry and server as-of time. The bilingual screen preserves its design, adds real hold creation and links from Units/stacking and to the lead drawer. Options search and pagination use actual active company leads, available units and assignees.

POST /reservations accepts unitId, leadId, unitVersion, hours (24/48/72), optional assigneeId and replay requestId. The service takes the shared company write lock, locks the unit before checking its reservation, recognizes expired holds, checks current inventory version/availability and inserts the new hold atomically. A new active hold changes the actual unit to hold. No arbitrary status editing or client-side fake availability.

POST /reservations/:id/action accepts current version and confirm/extend/cancel. Confirm requires an exact depositMinor string (zero is allowed), moves a hold to reserved and sets expiry to 72 hours from the database clock. This is a manually recorded deposit amount; it does not charge, collect or verify external funds. Extend requires a reason of 10–500 characters and 24/48/72 hours, added to current expiry and capped at 30 days from now. Cancel requires a reason and releases inventory, preserving the deposit/history. Closed or expired reservations cannot be edited. Contract conversion is performed by the subsequent contracts workflow, not simulated here.

Expiry is time-based. Reads use database now: expired holds appear expired immediately, and the security-invoker inventory_units view exposes the unit as available. Counts and stacking use that same view. Reads do not perform writes. The next write touching that unit persists expired reservation status, releases it, and records a system expiry audit/outbox/lead activity in the transaction. No background scheduler is claimed. Expiry recognition does not change the unit editing version, because availability already changes at its recorded expiry; explicit hold/confirm/cancel/edit operations do increment it. This allows the version visible after expiry to create/edit without a perpetual stale-version conflict.

All writes commit state, inventory, audit, outbox, lead activity and replay ledger together. Failures roll everything back. Create retries keep the original request body and version even if a prior response was lost and the unit is now held. Concurrent creates are serialized and the database uniqueness constraint remains a final guard.

Run npm run db:seed:reservations with isolated migration configuration, or node scripts/seed-reservations.mjs --company-slug=your-slug in maintenance. Default targets are only the three labeled sample companies with current subscriptions. It ensures sample leads/inventory and adds two clearly labeled, currently timed holds on available sample units. Existing, canceled or expired sample reservations are never reset on reruns. No fabricated payments, converted contracts or identities are seeded. No new environment secrets are required.
